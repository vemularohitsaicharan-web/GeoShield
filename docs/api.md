# API (Phase 10)

## What actually exists today

One real HTTP API: the Groq proxy server (`server/index.mjs`).

### `GET /api/health`
Returns `{ status: "ok", groqConfigured: boolean }`. Used by the app to distinguish three AI states: `ONLINE` (Groq key configured and proxy reachable), `FALLBACK_ONLY` (proxy reachable, no key — deterministic local analysis used instead), `OFFLINE` (proxy unreachable).

### `POST /api/analyze-report`
Request body: `{ "text": string, "signs": string[] }` (observed-sign IDs from `mobile/lib/types.ts`'s `ObservedSign` union).

Response (200): `{ "category": string, "severity": "LOW"|"MEDIUM"|"HIGH", "signals": string[], "summary": string, "confidence": number, "model": string }`, generated by Groq per the system prompt in `server/index.mjs`.

Response (502): `{ "error": string }` — the app's `mobile/lib/groqClient.ts` catches this (and network failures/timeouts) and substitutes a deterministic local classification instead, so a failed or unconfigured Groq call never blocks the report workflow.

No authentication on this API — acceptable for a same-device-network hackathon demo, not for any public deployment (see `docs/security.md` and `docs/deployment.md`).

## What's planned but not built

Phase 7 of `development-plan.md` specifies moving this behind a Supabase Edge Function boundary with the same request/response contract, plus four more AI endpoints (risk explanation, report summarization, alert message drafting, a responder Q&A assistant) once the Supabase backend from Phase 2 exists. The current proxy's contract was designed to be a drop-in match for that migration.
